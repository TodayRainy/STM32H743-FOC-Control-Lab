# 开发与实验工作流

目标是在保证安全和证据质量的同时，减少无意义的反复上电、端口扫描和重复测试。

## 任务分类

开始前先判断任务属于哪一类：

| 类别 | 典型工作 | 是否需要硬件 |
|---|---|---|
| 文档/规划 | 阅读、路线图、算法推导、报告 | 不需要 |
| 离线软件 | 代码审查、主机回归、静态检查 | 不需要 |
| 构建 | Keil build/rebuild、MAP/大小分析 | 不需要 24 V |
| 烧录/在线调试 | J-Link 写 Flash、读内存、断点 | 需要目标板供电；是否需要 24 V 取决于板卡供电结构和当前安全状态 |
| 串口观测 | 命令、遥测、软件示波器 | 需要串口设备和目标板运行 |
| 电机实验 | 电流、速度、位置、辨识、弱磁 | 需要用户明确确认 24 V 上电，并说明电机可能转动 |

离线任务不要为了“确认设备还在”而扫描 J-Link 或串口。

## 新窗口启动清单

1. 读取根目录 AGENTS.md。
2. 读取 docs/PROJECT_STATUS.md。
3. 根据任务读取 docs/HARDWARE_TOOLCHAIN.md、docs/ROADMAP.md 或 tests/README.md。
4. 查看 git status，识别已有修改和未跟踪文件。
5. 确认本次目标、停止条件和验证证据。
6. 若任务需要硬件，再询问用户当前电源、USB 和电机状态。

不要从上一个窗口最后一句“已上电”继续操作。新窗口中的硬件状态一律未知。

## 常规实现闭环

建议顺序：

1. 阅读相关源码和最近实验。
2. 写清本次假设、输入、输出和成功指标。
3. 先做离线推导或主机回归。
4. 进行最小范围代码修改。
5. 运行与改动风险相称的离线测试。
6. 使用指定 Keil 工程重新构建。
7. 检查构建日志、AXF/HEX/MAP 是否来自当前源码。
8. 规划一次连续硬件测试中的多个工况和安全阈值。
9. 告知用户需要上电、是否会转动以及预计测试范围。
10. 用户确认后烧录并执行批量测试。
11. 确认 STOP/READY，保存原始数据和报告。
12. 更新项目状态和重要决策。

如果只修改文档，到第 5 步即可，不要触发硬件链路。

## Skill 使用约定

| 任务 | 首选 Skill/工具 | 使用注意 |
|---|---|---|
| Keil 构建 | keil | 显式工程和 Target；确认 UV4 实际路径 |
| J-Link 烧录/调试 | jlink | 显式 V7.54d、设备、SWD、速率；检查原始输出和读回 |
| 串口命令/监控 | serial | 优先使用当前已知端口；失败或插拔后再扫描 |
| 持续交互终端 | terminal | 需要保持会话上下文时使用 |
| STM32 组合调试 | stm32-debug | 只有当其后端选择与本项目工具链一致时使用 |

Skill 的职责是执行。版本、路径、设备型号和实验边界由项目文档决定。若 Skill 默认行为与文档冲突，应显式传参或先修正配置，不能静默换后端。

## 构建

默认输入：

- Project：mdk/STM32H743VGT6_FOC.uvprojx
- Target：STM32H743VGT6_FOC
- UV4：D:\STM32\keil5\Core\UV4\UV4.exe

预期输出：

- mdk/build/STM32H743VGT6_FOC.axf
- mdk/build/STM32H743VGT6_FOC.hex
- mdk/build/STM32H743VGT6_FOC.map

构建完成应记录：

- error/warning 数量；
- 编译器实际版本；
- 产物时间；
- 代码/只读数据/RAM 大小的明显变化；
- 当前工作区是否仍有未构建修改。

不要因为已有 HEX 就跳过当前源码的构建。

## 烧录

默认使用独立版 J-Link V7.54d。烧录前：

- 确认当前 HEX 是刚刚构建的；
- 确认目标设备 STM32H743VG；
- 告知用户是否需要 24 V，以及固件复位后是否可能自动启动；
- 若串口正在占用或软件示波器正在采集，先结束会话。

烧录后至少核对原始日志；在工具封装曾出现误判、Flash 异常或更改链接布局时，读回向量表或关键地址。

24 V 接通时可以烧录，但它不是默认无条件操作。必须确认固件在复位后保持安全输出，并让用户知道板卡将复位。

## 高效率硬件测试

一次实验前先定义测试矩阵。例如：

- 电流：0、+0.2 A、-0.2 A、0；
- 速度：500、1500、3000 rpm，必要时正反向；
- 位置：小角度正反阶跃和回零；
- 算法开关：同一轨迹下前馈 OFF/ON。

测试矩阵应同时定义：

- 最大允许电流；
- 最大允许速度；
- 母线电压范围；
- 每点持续时间；
- 异常停止条件；
- 最终必须确认的 READY/STOP 状态。

用户未重新插拔且串口正常时，直接使用已有端口，不把时间浪费在重复枚举。只有打开失败、帧超时、数据格式错误或用户说明硬件变化时才排查端口。

不要为了“自动化”盲目扩大速度和电流范围。自动化用于覆盖已批准的工况，不扩大硬件授权。

## 软件示波器

串口是首选导出路径：

1. ARM 指定分频；
2. 控制中断向内存缓冲采样；
3. 捕获完成后 DUMP；
4. 主机保存 CSV；
5. 离线计算指标。

这避免在 40 kHz 中断中直接发送串口。当前 4096 点、10 通道和三档分频已足够支撑阶段 0 及初期辨识。只有新算法确实需要其他变量时才修改协议和通道。

串口不可用时可通过 J-Link 根据 MAP 符号读取控制块和采样缓冲。J-Link 读取是后备能力，不需要为每次串口成功采集重复读取一份。

## 异常处理

遇到异常时按最短路径处理：

- 电流、速度超阈值或失控迹象：立即 STOP；若无法确认停止，通知用户断电。
- 串口超时：先发送 STOP，再判断是采集时间、端口还是目标状态；不立刻重新烧录。
- 烧录失败：查看原始输出，reset + halt 后重试；不要连续尝试多个 J-Link 版本。
- 模式未进入：保留遥测和模式码，区分校准失败、命令失败和状态机条件。
- 工具结果矛盾：优先原始日志、读回和实际数据，不依据摘要字段强行继续。

保护代码保持简单、与已观察风险对应。不要因单次工具故障在固件中加入多层无关防御。

## 实验记录

每次能形成结论的实验至少记录：

- 日期和脚本；
- 固件构建或提交标识；当前没有提交时记录工作区状态；
- 电源、电机和负载条件；
- 测试参数；
- 原始 CSV/JSON 路径；
- 指标和观察；
- 结论适用范围；
- 尚不能解释的现象。

原始数据留在 tests/results。项目状态只摘要最重要结论，不复制全部波形。

## 会话结束与交接

完成实质工作后：

1. 更新 docs/PROJECT_STATUS.md 的完成项、证据和下一步；
2. 若改变方案，更新 docs/DECISIONS.md；
3. 若改变中长期方向，更新 docs/ROADMAP.md；
4. 告知用户是否还需要保持上电；
5. 给出下一窗口可以直接使用的任务描述。

相关工作可在同一窗口连续推进；当上下文开始混入多个阶段、工具状态难以区分，先完成文档检查点，再开启新窗口。
